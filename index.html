Predicting Content Decline: A Refresh Prioritization Study

Can a Logistic Regression model beat a simple visibility + staleness rule at flagging content for refresh?

Abstract. I set out to compare a simple hand-written rule against a Logistic Regression model to see which one does a better job flagging content pages for refresh. The rule marks a page as high-priority (REFRESH) when it has more than 80 impressions in the last 90 days and hasn't been updated in over 51 days; everything else falls into REVIEW or NO_ACTION. The LR model uses 23 features instead of just two, and after fixing a data leakage issue, its accuracy came out almost identical to the rule's. The result is directional — useful for ranking content, not for making final calls on its own.

1. Introduction / Problem Statement

The question I wanted to answer was whether a model trained on content signals could reliably flag pages at risk of declining performance — and whether it could actually beat a basic impressions + staleness rule at doing that. The practical use case is prioritization: given a content library, which pages should get refreshed first? The output is a ranked list — REFRESH, REVIEW, or NO_ACTION — for each page.

2. Data

The main dataset here is content_refresh_anonymized.csv, the FlyRank ML Internship dataset — 30,000 rows, 44 columns of content-performance data, used for both the rule-based baseline and the LR model. I also explored the full FlyRank Warehouse dataset on Hugging Face during Weeks 3-4 for feature exploration, but that data isn't part of the final trained model. Two columns — trend_direction and trend_pct — were excluded from training since they directly reflect the outcome I was predicting; using them would leak the answer into the model. They were only used to build the decline label itself. No client names, URLs, or private queries appear anywhere — the dataset is fully anonymized.

3. Methodology

I treated a page as "declining" when it showed high visibility combined with low recent engagement or staleness — same basic logic as the rule, just applied through more variables. Instead of the rule's two fixed signals, the model gets access to 23 numeric columns: things like search_volume, competition, cpc, word_count, impressions_90d, clicks_90d, pageviews_90d, sessions_90d, days_since_last_update, ctr, avg_position, engagement_rate, ai_traffic_pct, and others — everything left after removing the leakage-prone columns.

The label, is_declining, is set to 1 when trend_direction is 'down' and 0 otherwise. trend_direction and trend_pct themselves were dropped from the features since they're literally what the label is built from — keeping them in would be leakage. I also removed impressions_last_30d, clicks_last_30d, sessions_last_30d, impressions_prev_30d, clicks_prev_30d, and sessions_prev_30d, since these overlap directly with the time window used to define the label.

The baseline rule: if impressions_90d is above 81 and days_since_last_update is at least 51, the page gets flagged HIGH_VISIBILITY_STALE and marked for REFRESH; other combinations fall into REVIEW or NO_ACTION. The model itself is Logistic Regression, trained on the 23-feature set above. I first validated with an 80/20 stratified split (stratified on the label, not time- or group-aware), then re-checked with a client-grouped split. On the leakage side, I initially noticed accuracy jump when the trend/window columns were left in, which is what led me to remove them. I also tested a second batch of suspect 90-day aggregate columns (impressions_90d, sessions_90d, clicks_90d, pageviews_90d, users_90d, engaged_sessions_90d) under the grouped split — accuracy only moved from 0.583 to 0.578 when they were dropped, less than a one-point difference, so I kept them since they weren't giving a hidden shortcut.

Neither version is close to being decision-ready — at best, both are useful as a way to flag content for a human to look at.

5. Limitations & Honest Framing

One thing that stood out: about 80% of rows share just three distinct values for days_since_last_update. That's almost certainly a byproduct of how the dataset was generated or anonymized, not a real reflection of content age — so staleness on its own isn't a signal I'd trust. This ties into the split issue too: performance looked good under a random 80/20 split, but dropped close to the base rate once I used a grouped split. That gap shows how a random split can make results look better than they actually are when rows aren't independent (e.g., multiple rows from the same client).

Everything here comes from one anonymized dataset (30,000 rows) and one train/test setup — no cross-validation, no second dataset to confirm the pattern holds. So this is a directional read, not a final verdict. There's also an asymmetry worth naming: the baseline uses just two signals, the model uses 23 — but even 23 doesn't touch things like content_type, main_intent, provider_used, or deeper behavioral history. There's likely more predictive signal sitting unused.

None of this shows causation — a link between visibility/staleness and decline isn't proof that refreshing a page will actually fix performance, and this isn't an attempt to reverse-engineer any search engine's ranking logic. Given how small the model's edge over the baseline is, and how much it depends on the split method, this should support a human reviewer's prioritization call — not trigger any refresh action on its own.

6. Ranked Recommendations

The rule stays the same as the baseline: visibility (impressions_90d) is the confirmed driver of decline, while staleness (days_since_last_update) is a mixed, non-monotonic signal — used only as a tiebreaker among already-high-visibility pages, never as the primary trigger. Within each reason code, pages are ranked by impressions_90d, so the highest-traffic items surface first — that's where a missed fix matters most. On this snapshot: 36.65% of pages landed in REFRESH, 63.35% in REVIEW (30,000 rows total, base decline rate 0.5421).

REFRESH picks concentrate almost entirely in "keyword article" content, which makes up 91% of the dataset — smaller content types like comparison articles get few or zero REFRESH flags in this snapshot. That's a reflection of where the queue currently concentrates effort, not a claim that other content types never need refreshing. On the staleness side, decline rate by bucket is non-monotonic — it dips at 21–50 days, peaks at 51–104, then dips again past 105 — and about 80% of rows are stuck on just 3 repeated values for days_since_last_update. That pattern looks more like a data artifact than actual content age, which is why staleness only ever plays tiebreaker, never the main driver.

Human review checklist before acting on any REFRESH/REVIEW pick:

  • Does days_since_last_update actually match the CMS edit history? (given the artifact, don't trust it blindly)
  • Is this evergreen/reference content that doesn't need updating regardless of score?
  • Is the traffic a one-off spike that'll settle by itself?
  • Is one outlier client skewing the numbers?

What should never be automated: auto-publishing content changes, permanently writing off LOW_VISIBILITY pages, treating the reason code as an explanation for why a page is declining, or reusing the thresholds (81 impressions, 51 days) on a new client without re-validating them.

Monitoring triggers: re-check base rate drift, whether the staleness artifact is changing shape, and whether the REFRESH/REVIEW/NO_ACTION split moves far from roughly 27%/48%/25% — any of that means redoing the signal-check-rule-validate cycle, not just reusing old cutoffs.
